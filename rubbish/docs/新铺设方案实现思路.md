# 新铺设方案实现思路

> 目的：基于 `.docs/异种地图开发思路.txt` 中"下一阶段"描述的新铺设方案，分析其实现思路，
> 重点解决"奇偶旋转等不好实现"的问题，提出合并单元为真正平移循环块的折中方案，
> 并规划解析几何优化路径。

---

## 1. 背景与问题

### 1.1 当前实现现状

- **数据结构**：`data/tiling_specs_arch.json` 和 `tiling_specs_laves.json` 定义密铺几何，每个类型有一个平移循环块（B个基础格）。
- **worldToCell实现**：对表驱动密铺使用暴力搜索（O(B)复杂度），如 `Tiling.cpp:547` 所示。
- **块内格子数量**：不同密铺差异显著：
  - arch_33434: 6格
  - arch_33336: 18格  
  - arch_3464: 8格
  - laves_4612: 24格（最高）

### 1.2 文档描述的新方案

`异种地图开发思路.txt` 第403-437行描述了更精简的密铺单元块：

- **arch_33434**：3格（歪正方形+两个三角形），但需根据行列奇偶性旋转60°。
- **arch_33336**：8格（六边形+8个三角形），平移逻辑复杂（每到下一列向上平移，每到下一行向左平移）。
- **arch_3464**：7格（六边形+3个正方形+2个三角形），奇数行右移。
- **其他类型**：均有类似复杂放置逻辑。

### 1.3 核心矛盾

`gen_tiling_specs_v2.py` 注释（第8-16行）明确指出：

> 引擎只有纯平移放置、没有按 (r,c) 奇偶镜像/旋转的放置 —— 要把块内格数缩下去就必须支持这种放置或用斜周期，二者都会破坏"矩形地图"这一硬性要求。

即：**更精简的块需要奇偶旋转/镜像，但引擎当前不支持**。

---

## 2. 方案分析

### 2.1 方案一：实现奇偶旋转（复杂）

- **优点**：块内格子数量最少（如arch_33434仅3格）。
- **缺点**：
  - 需修改引擎核心逻辑（cellCenter、worldToCell、neighbor等）。
  - 增加代码复杂度，易引入bug。
  - 可能破坏矩形地图的硬性要求。

### 2.2 方案二：合并单元为真正的平移循环块（推荐）

- **优点**：
  - 保持纯平移放置，无需修改引擎核心逻辑。
  - 代码简洁，维护成本低。
  - 与当前实现兼容，可平滑过渡。
- **缺点**：
  - 块内格子数量增加（如arch_33434从3格增至6格）。
  - 可能影响性能（但可通过解析几何优化补偿）。

### 2.3 方案三：斜周期（破坏性）

- **优点**：理论最优块大小。
- **缺点**：
  - 破坏矩形地图要求。
  - 需重写chooseTableDomain、worldWidth/Height等函数。
  - 实现复杂，风险高。

---

## 3. 推荐方案：合并单元 + 解析几何优化

### 3.1 合并策略

**目标**：将多个基本单元合并为一个真正的平移循环块，保持纯平移放置。

**具体实现**：

1. **对于需要奇偶旋转的类型**（如arch_33434）：
   - 将两个旋转状态（0°和60°）合并为一个更大的平移循环块。
   - 当前tiling_specs_arch.json中arch_33434已有6格，可能已是合并结果（验证：文档描述3格，实际6格，符合2倍关系）。

2. **对于需要复杂平移的类型**（如arch_33336）：
   - 将多个基本单元合并，使平移向量变为轴对齐（W=(wx,0), H=(0,hy)）。
   - 块内格子数量增加，但平移逻辑简化。

3. **保持方向规范**：
   - 使用`gen_tiling_specs_v2.py`的方向纠偏逻辑（rot90函数），确保数据方向正确。
   - 运行时无需额外旋转/镜像。

### 3.2 解析几何优化

**目标**：为每种密铺类型实现专门的worldToCell优化，降低单次查询复杂度。

**优化路径**（基于文档第442-466行描述）：

#### 3.2.1 类正方形密铺（arch/laves 4.8.8, 3.3.4.3.4）

- **思路**：先确定点在哪个正方形区域内，再判断具体格。
- **实现**：
  ```
  1. 计算点在哪个"大正方形"区域（行列整数除法）。
  2. 对arch 4.8.8：与四条直线判断，确定在小正方形还是大八边形。
  3. 对laves 4.8.8：与大正方形两条直线判断方向，确定在哪个三角形。
  4. 对arch 3.3.4.3.4：与四条直线判断，确定在小正方形还是三角形。
  5. 对laves 3.3.4.3.4：先划分为四个小正方形，再与一条直线判断。
  ```

#### 3.2.2 类三角形密铺（laves 3.12.12, 3.4.6.4）

- **思路**：套用三角形密铺逻辑，再在三角形内判断。
- **实现**：
  ```
  1. 使用三角形密铺的worldToCell逻辑定位到三角形。
  2. 在三角形内，根据水平坐标判断左右。
  3. 与左侧或右侧斜直线判断具体在哪个三角形内。
  ```

#### 3.2.3 类六边形密铺（arch 3.12.12, 3.4.6.3.6, 4.6.12）

- **思路**：先判断六边形区域，再与直线判断。
- **实现**：
  ```
  1. 将三角形中心相连得到六边形密铺格。
  2. 判断点在哪个六边形内（类似六边形密铺逻辑）。
  3. 在六边形内，根据距离和直线判断具体格。
  ```

#### 3.2.4 特殊类型（arch/laves 3.3.3.3.6）

- **思路**：需单独分析，可能结合多种方法。
- **建议**：先完成其他类型优化，再专门处理。

### 3.3 性能权衡

| 方案 | 块内格子B | 单次查询复杂度 | 实现难度 | 风险 |
|------|-----------|----------------|----------|------|
| 当前实现 | 6~24 | O(B×9×n) | 低 | 低 |
| 奇偶旋转 | 最小（3~8） | O(1)~O(n) | 高 | 高 |
| 合并单元+几何优化 | 中等（6~24） | O(n)~O(n²) | 中 | 低 |

**结论**：合并单元+几何优化在实现难度、风险和性能间取得平衡。

## 4. 实施步骤

### 4.1 第一阶段：数据准备

1. **验证当前数据**：检查`tiling_specs_arch.json`和`tiling_specs_laves.json`是否已包含合并后的块。
2. **重新生成数据**（如需要）：使用`gen_tiling_specs_v2.py`生成符合方向规范的数据。
3. **确保轴对齐**：所有数据的W=(wx,0), H=(0,hy)，无斜周期。

### 4.2 第二阶段：解析几何优化

按优先级实现：

1. **类正方形密铺**（arch/laves 4.8.8, 3.3.4.3.4）：
   - 实现基于区域划分的快速判断。
   - 预计算直线方程，避免运行时重复计算。

2. **类三角形密铺**（laves 3.12.12, 3.4.6.4）：
   - 复用三角形密铺逻辑。
   - 在三角形内添加斜直线判断。

3. **类六边形密铺**（arch 3.12.12, 3.4.6.3.6, 4.6.12）：
   - 实现六边形区域定位。
   - 在六边形内添加距离和直线判断。

4. **特殊类型**（arch/laves 3.3.3.3.6）：
   - 单独分析，设计专门算法。

### 4.3 第三阶段：测试与调优

1. **单元测试**：为每种密铺类型编写worldToCell测试用例。
2. **性能测试**：对比优化前后的查询性能。
3. **确定性测试**：确保优化不影响游戏确定性。
4. **视觉测试**：用户测试密铺边界、城市形状等视觉效果。

## 5. 注意事项

1. **不要更改.txt文档**：按用户要求，不修改`.docs/异种地图开发思路.txt`。
2. **保持兼容性**：新实现应与现有数据格式和API兼容。
3. **性能监控**：优化后需跑确定性测试（最小地图，2000tick，城密度适当高）。
4. **文档更新**：完成后更新相关开发文档。

---

## 6. 总结

推荐采用**合并单元为真正平移循环块 + 解析几何优化**的方案：

- **合并单元**：保持纯平移放置，简化引擎逻辑，降低实现风险。
- **解析几何优化**：为每种密铺类型实现专门的快速判断，补偿块增大带来的性能损失。
- **分步实施**：先优化类正方形密铺，再扩展到其他类型，最后处理特殊类型。

此方案平衡了实现复杂度、性能需求和代码维护性，符合项目"确定性可复现"的核心要求。
