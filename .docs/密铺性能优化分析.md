# 已支持密铺的数学性能优化分析

> 目的：分析项目中已实现的 10 种密铺（5 半正 + 5 Laves）在运行时卡顿的数学/算法根源，
> 给出可落地的性能优化方案。重点：为什么 Laves 密铺（尤其 B 大的）卡顿最明显。
> 所有结论基于对项目代码（C++ 引擎 + Python 生成工具）的实际阅读与实验。

---

## 1. 性能画像：卡顿发生在哪

### 1.1 卡顿不是渲染层

渲染路径（`MapRenderer::drawTiled`）对每个可见格：

- `cellPolygon`：表驱动分支是 **O(1)** 直接查表平移（基础格顶点 + 行列偏移），
  无逐格搜索；
- `cellCenter`：O(1) 查表；
- 顶点批处理（SDL vertex batching）已实现。

所以**可见格数量 × O(1)** 的渲染开销对 10 种密铺一致，不是 Laves 更卡的根因。

### 1.2 卡顿在"世界坐标 → 格"查询（worldToCell）

模拟中**每 tick 每个兵/子弹/特效**多次调用 `worldToCell`：

- `SpatialHash::bucketIndex`（空间哈希重建，每 tick 全量）；
- `MovementSystem`（移动中每步穿越判定，多次）；
- `ProjectileSystem`、`EffectSystem`、`SpawnSystem`（每帧定位）；
- 城市形状解析（`Map::shapeCells` / `placeableVariants`）。

对**表驱动密铺**，当前 `worldToCell` 实现为（见 `Tiling.cpp`）：

```
对每个基础格 b ∈ [0, B)：
    解线性方程 p - center_b = c·W + r·H → 候选 (c0, r0)
    对 (r0±1, c0±1) 的 9 个候选：
        重建平移多边形（b 的顶点 + 平移）
        凸多边形点包含测试（点与每条边叉积）
        命中 → 返回
```

**单次查询复杂度 = O(B × 9 × n)**，其中：
- B = 周期域内基础格数（Laves 最高达 24，如 Laves4612）；
- n = 多边形边数（Laves 最高 5，Arch 最高 12）；
- 每次还重建多边形顶点（浮点乘加）。

**为什么 Laves 最卡**：
- Laves 的 B 普遍大于半正（Laves4612 = 24、Laves31212 = 12、Laves3464 = 12，
  而 Arch 多为 6~12）；
- 最坏单次查询 = 24×9×5 = **1080 次叉积**（含浮点除法/平移）；
- 每 tick 数千次查询 × 模拟时长 → 累积巨大。

### 1.3 次要热点

- `crossEdge`（移动穿越）：对表驱动类型，几何仍是 O(1) 边求交，但调用频繁；
  若内部再调 `worldToCell` 重定位，则叠加 1.2 的开销。
- `SpatialHash::queryAABB/queryCircle`：`rowRange/colRange` 对表驱动是 O(1) 公式，
  但每个候选 (r,c,b) 的桶访问是 O(1) —— 非瓶颈。
- 城市形状放置/解析（地图生成一次性）：`placeableVariants` 对每个锚格 × 每个变体
  调 `worldToCell`，生成期慢但非运行时。

## 2. 数学优化方案（核心）

### 2.1 方案 A：worldToCell 线性化（最大收益，首选）

**数学基础**：表驱动密铺的格中心是仿射格点阵（affine lattice）：

```
center_b(r, c) = C_b + c·W + r·H
W = (wx, 0),  H = (hx, hy)   （周期向量，H 可斜）
```

对任意世界点 P，求解（对每个 b）：

```
P - C_b = c·W + r·H
⇒  c = (Px - C_bx)/wx - (hx/wx)·(Py - C_by)/hy
⇒  r = (Py - C_by)/hy
```

这是**两个除法 + 一次乘减**（O(1)），得到候选 (c0, r0)。当前实现已经这样算，
但问题在于**它只验证一个 b 就做 9 格窗口 + 多边形重建**，且**必须遍历所有 b**
因为不知道点属于哪个 b。

**优化 1：预计算"b 的 Voronoi 归属表"（决定性改进）**

对每个基础格 b，其格中心在仿射格上的位置是确定的。可以预计算一个"查询哈希"：

- 取一个足够大的**格点邻域采样**（例如每个 b 周围采样 N×N 个点，用精确
  worldToCell 标记归属），建立"世界坐标 → 基础格 b"的查找表（按周期取模）；
- 查询时：先按周期向量把世界点折算到域内（O(1) 取模），再查表得候选 b；
- 只对候选 b 做 3×3 窗口验证（退化到与方/六/三同量级）。

**优化 2：直接反解 b（几何双线性）**

注意到整个周期域的格中心构成一个**二维仿射格 + 域内有限个偏移**。可以把
"P → (b, r, c)"看作：先在斜坐标系 (W,H) 中解出连续坐标 (u, v)：

```
[u; v] = M⁻¹ · (P - C_0)    其中 M = [W, H]（2×2 矩阵，预求逆）
```

得到 (u, v) 后，取整得到候选 (r, c)；此时只需在**域内所有 b** 中找中心离
P 最近的那个（因为同一 (r,c) 下 B 个 b 的偏移是确定的、且 B 有限）。

- 预计算：对每个 (r,c) 偏移量 Δ = C_b - C_0（b 个向量）；
- 查询：解出 (u,v) → (r0,c0)（O(1)）；对 (r0±1, c0±1) 的 9 个 (r,c)，
  每个比较 B 个偏移 Δ_b 的"点到中心距离平方"（O(B) 乘加，无浮点除法）；
  再对最近 1~2 个候选做精确凸包含测试。

**复杂度从 O(B×9×n) 降到 O(9×B)（纯乘加）+ O(1) 次精确测试**。对 B=24、
n=5 的情况，从 ~1080 次叉积降到 ~200 次乘加 + 1 次叉积。预估 5~10 倍提速。

### 2.2 方案 B：凸包含测试向量化/免重建

当前凸包含测试每次重建多边形（`std::vector` 分配 + 平移）。优化：

- **预计算每个 b 的"边法向 + 常量"**（相对中心的半平面表示）：
  多边形 = 若干半平面 { x·nx_i + y·ny_i ≤ d_i }（中心为原点）。
  查询时：对候选 (r,c)，把 P 平移回域内（减 C_b + 平移），直接对预计算的法向
  做 k 次点积（O(n) 乘加），**无内存分配、无除法、无多边形重建**。

这使"精确测试"从"重建+叉积"变成"纯点积"，是方案 A 的补充（或独立使用）。

### 2.3 方案 C：缓存最近查询（时间局部性）

兵/子弹位置连续变化，世界坐标与上一次查询往往在同一格或相邻格。可加一个
**单元素或小环形缓存**（最近 N 次 (x,y)→idx），查询时先做近邻距离检查。
对移动系统（位置逐 tick 连续）命中率极高。实现简单、零风险。

### 2.4 方案 D：空间哈希桶直接按 (r,c,b) 构建

`SpatialHash::bucketIndex` 目前对非方形走 `worldToCell`。若改为：

- 由位置先解 (u,v)（方案 A 的线性化）得候选 (r,c,b)，或
- 维护实体上一格，移动时只用 `crossEdge` 的边穿越结果更新 (r,c,b)
  （不需要从世界坐标重新解），

可把"每 tick 全量重建空间哈希"从 N×worldToCell 降到 N×O(1) 邻接更新。
这需要 SpatialHash 与 MovementSystem 协调（重建时用世界坐标，移动后增量维护），
改动较大但收益显著（空间哈希是每 tick 最频繁的 worldToCell 调用方之一）。

### 2.5 方案 E：渲染缓存

若渲染仍是潜在瓶颈（放大缩小/大地图），可对每个基础格 b 预计算：

- 顶点缓冲（一次性，不逐帧重建）；
- 若相机平移为主，可用"格索引 → 屏幕多边形"的缓存（按键 (r,c,b) 失效）。

但按 §1.1 渲染已是 O(1)/格，此项收益有限；列为可选。

## 3. 各密铺的复杂度对照

| 密铺 | B | 面型（边数 n） | 单次 worldToCell 最坏操作（当前） |
| :--- | :--- | :--- | :--- |
| 方/六/三 | 1~2 | 4/6/3 | O(1) 公式（无遍历） |
| Arch3464 | 12 | 3/4/6 | 12×9×6 ≈ 648 |
| Arch3636 | 6 | 3/6 | 6×9×6 ≈ 324 |
| Arch31212 | 6 | 3/12 | 6×9×12 ≈ 648 |
| Arch4612 | 12 | 4/6/12 | 12×9×12 ≈ 1296 |
| Arch488 | 8 | 4/8 | 8×9×8 ≈ 576 |
| Laves3464 | 12 | 4 | 12×9×4 ≈ 432 |
| Laves3636 | 6 | 4 | 6×9×4 ≈ 216 |
| Laves31212 | 12 | 3 | 12×9×3 ≈ 324 |
| Laves4612 | 24 | 3 | 24×9×3 ≈ 648 |
| Laves488 | 4 | 3 | 4×9×3 ≈ 108 |

（注：实际命中大多在第 1~2 个 b 就返回，平均低于最坏；但 Laves4612 等 B 大的
密铺在**未命中**（界外/海陆判断失败重试）时最坏路径被频繁走完。）

**结论**：卡顿与 B（基础格数）和 n（边数）强相关；Laves4612/Arch4612/Arch31212
等 B×n 大的密铺最卡。方案 A（线性化 + 预计算偏移表）对这类密铺收益最大。

## 4. 落地建议（按收益/风险排序）

1. **（低风险、高收益）方案 A + B 组合**：重写 `worldToCell` 表驱动分支
   （线性化 + 预计算偏移/法向，无分配），保留现有确定性扫描序
   （b 升序、r 邻域 -1..1、c 邻域 -1..1）以保证 RNG/回放兼容。预期 5~10 倍。
2. **（低风险）方案 C**：移动/子弹系统加最近查询缓存（不改扫描序，命中即返回）。
3. **（中风险）方案 D**：空间哈希增量维护（需要与 MovementSystem 的 `crossEdge`
   结果联动）。若 1+2 已达标可不做。
4. **（可选）方案 E**：渲染顶点缓存。

所有优化**必须保持世界坐标→格的下标确定性**（`worldToCell` 的扫描顺序
b 升序 → 邻域序），否则会改变 RNG 序列 → 基线 hash 漂移、回放不兼容。
方案 A 的线性化只是"缩小候选集"，最终仍走同一验证序，可保证位级一致。

## 5. 验证方法

- 性能基准：对每种密铺，生成中大地图（如 200×200×B），空跑 N 个 tick 的
  移动/空间哈希，统计 `worldToCell` 总调用次数与耗时（Debug/Release 各一次）。
- 正确性：全部 404+ 非基线测试通过；`worldToCell` 的随机点采样对比新旧实现
  （数十万随机点逐位一致）。
- 基线：优化不改 RNG 序列 → `--headless --seed 42` 基线 hash 不变
  （待幂律恢复后重跑确认）。
